## 5.D On input (3.2.2; Forms, pp. 25 and 27)

**What the PDF asks.** Identify form elements (p. 25, Identify Content; ANDI
as an inventory, disabled elements excluded; none on the page: DNA). For
each: navigate to it with the keyboard, complete it (select the radio or
checkbox, type into the text box, pick from the drop-down), tab away, and
decide whether an unexpected change of context happened (p. 27, HtT 1–3).
Changes of context: user agent, viewport, focus, content that changes the
meaning of the page; for example a form submitted on leaving a field, a new
window from a radio button (HtT 4). Not unexpected if the user was told
beforehand, or the control is clearly meant to change context (HtT 4.a).
Note: a text field may need focus moved away before its input event fires.

**Reuse.**
- Fields come from the walk's stops (`stop.field`, role, tag), not ANDI:
  the same reasoning as 4.A's inventory (real key presses, frames and shadow
  roots), with the DOM inventory as the cross-check for DNA.
- `ctx.replay(keys)` to each field: quick prefixes and the arrival check
  (4.C spec section 2, 1.7.0).
- 4.A's `observe(s, quiet_ms, act, path_key)` records exactly the effects the
  PDF lists: navigation, frame navigation, new page, dialog, focus moved,
  DOM change. `act` is "complete the field, then Tab". Move `observe` and
  `Effect` out of t4a.py into a shared module (e.g. `observe.py`) so 4.A,
  4.B and 5.D import it from one place, rather than 5.D importing t4a.
- 4.E's question pattern for "was this change expected?" (J1 with
  `changes_context` / `content_only`, page text near the element, before
  and after images) and its rubric wording.
- Safety comes from the recording: the replay serves only what was
  recorded, so a form that submits on input posts to nothing (the request
  fails) and the navigation guard still enforces the allowlist. Record that
  as evidence (an attempted submission is itself the signal), never send
  anything live.

**Draft rules (to confirm in the spec).**
- DNA: no form fields among the stops and none in the inventory.
- Per field, one fresh replay: complete it (by kind, below), press Tab, and
  observe. No effect, or only a DOM change inside the field's own widget
  (an autocomplete list), is no change of context for that field.
- Navigation, a new page, a submission attempt or focus moving somewhere
  other than the next stop: a change of context. FAIL unless the user was
  told beforehand; that is an open question (J1) with the text before the
  field and the field's name and description, asked only when the signal is
  mechanical. "Clearly intended to change context" applies to controls like
  submit buttons, which 5.D does not complete (Q4).
- A DOM change elsewhere (new fields appear, a section opens): whether it
  "changes the meaning of the page" is an open question, as 4.E's
  `content_only` answer; content that only reveals related fields is the
  common, passing case.
- Every field tried, none with an unexpected change: PASS (mechanical:
  the key presses confirm it). Fields not tried (cap, time): NEEDS REVIEW.

**Open points for Abby** (multiple choice, recommendations first):
- Q2. Text field values: (a) a fixed neutral value per input type, recorded
  in the report (recommended: "Test", `test@example.gov`, `2026-01-15`,
  `12345` for numeric and `inputmode=numeric`, max length respected);
  (b) the agent suggests a value per field from its label (like 4.C's form
  suggestions); (c) both: fixed first, agent's on a follow-up.
- Q3. Auto-advance (a field moves focus to the next one when full, e.g.
  phone parts): (a) a change of focus, so a change of context; FAIL unless
  the user is told (recommended, HtT 4 lists focus); (b) expected behavior,
  PASS; (c) always NEEDS REVIEW.
- Q4. Which elements: (a) text fields, text areas, radio groups (one change
  per group: an arrow to the next option), checkboxes (Space), selects
  (ArrowDown on the closed select: it changes the value in Linux headless
  Chromium, checked 2026-11-01; Windows Chrome not yet checked), switches
  and comboboxes; buttons and links excluded,
  since activating them is meant to act (recommended); (b) also custom
  widgets with roles (sliders, spinbuttons: one arrow press).
- Q5. Cap: (a) `FIELD_MAX` 25 fields, one replay each, about 1–3 s each with
  quick prefixes; the rest NEEDS REVIEW "not every field was tried"
  (recommended); (b) every field, relying on the run limit.
- Q6. Selects on Mac open a popup on ArrowDown instead of changing the
  value. Results are per browser and platform the report records; the
  server runs Linux or Windows Chrome. (a) note it in the spec and the build
  tasks (recommended); (b) also change the value with
  `select_option` as a fallback (not a key press, so evidence only, never a
  PASS on its own).

**Fixtures.** Section 508 Baseline Alignment cases for 3.2.2 first (the
framework has cases for "form submitted, new window, focus moved"; vendor
with `tests/fixtures/baseline/sync_baseline.py` and load them in Chrome
first). No W3C ACT rule covers 3.2.2. Custom pages only for gaps: a select
that navigates on change (jump menu, F37-like), the same with a notice
before it, a radio that opens a new window, a form that submits when its
last field is left (F36), an auto-advancing phone field, a checkbox that
reveals more fields (passing content change), an autocomplete list (no
change of context), a field inside an iframe.

**Time.** One replay per field. The benefits form (`tests/fixtures/budget/`)
has about 25 fields: about 25–50 s more on top of today's 83 s, so close to
the limit. Measure with `evals/time_budget.py` while building and decide on
the cap (Q5) from that; sharing replays may come back as an option here.

## 9.A Bypass (2.4.1; Repetitive Content, pp. 42–43)

**What the PDF asks.** Identify blocks repeated on other pages (navigation,
headers, tabs, banners; not exactly identical; small sections and single
links excluded; a block at the bottom may need no bypass). From the top,
navigate forward to the repeated blocks (a bypass may appear only on focus),
find a keyboard method to bypass them (skip links, hotkeys, scripted
elements; frames in some browsers), and activate it (HtT 1–3). Several blocks
may need several methods; with nothing focusable after the block, the move
may not show (HtT 3.a, 3.b). PASS if a keyboard method exists and, when
activated, bypasses the block (ER 1, 2), without skipping content that is
not repetitive (Note 2). DNA if no block repeats on other pages.

**Reuse.**
- The walk's first stops and their link targets: in-page links (`#id`) and
  buttons before the main content are the candidates; 4.D's F03 skip-link
  fixture and the agency-home page are ready test pages.
- `ctx.replay` to the candidate, Enter, then Tab once: where the next stop
  falls in P1's order shows what was bypassed (Chrome moves the sequential
  focus starting point to a non-focusable target, so the next Tab lands
  after it: checked in Linux headless Chromium 2026-11-01, with a skip link
  to a `div` holding an `h1`; Windows Chrome is a build-task check). The bypassed range is the
  P1 stops between the link and the landing stop.
- 4.F's landmark and region information for where the main content starts
  (the `main` element or landmark, the first `h1`), as evidence for the
  question, never as the bypass itself.

**The decision that shapes it (Q1).** One page cannot show what repeats on
other pages, and page content must never choose a URL to visit (principle
5), so the tool cannot follow the site's own links to find out.
- (a) The agent judges by looking: the question shows the stops before the
  main content with their landmarks (header, navigation) and asks whether
  they form a block repeated across the site, the spec marking it as one a
  careful tester settles by looking (like 4.E J1); "unsure" goes to a person.
  Recommended for now: it matches how testers work on a single page.
- (b) An optional input on `a11y_run_tt_tests`: other pages of the same site
  (each checked against the allowlist), recorded and compared mechanically
  (same blocks by text and structure). Exact, and the base for 9.B and 9.C,
  but a multi-page run is new pipeline work.
- (c) (a) now, (b) when 9.B/9.C are built, reusing the same input.

**Other open points.**
- Q7. Landmarks and headings as the bypass method: the PDF lists skip links,
  hotkeys and scripted elements (and frames); W3C's ACT bypass rule (cf77f2)
  also accepts landmarks and headings, which need assistive technology for
  keyboard users. (a) Not a keyboard method on their own: with blocks but
  no skip link, hotkey or scripted method, FAIL (recommended, as the PDF
  reads); (b) count them, as ACT does; (c) NEEDS REVIEW. Check DHS's verdicts
  on the cf77f2 cases in their ACT implementation report before asking.
- Q8. Skips too far (Note 2: the landing is past the start of the main
  content): (a) FAIL when the landing stop is after the first stop inside
  `main` (or after the first `h1` when there is no `main`), mechanical;
  (b) an open question. Recommended (a), with (b) when the page has neither.
- Q9. Hotkeys and scripted methods: (a) tried only when the page text
  documents a key (as 4.C's documented keys: J-style question, then the
  tool presses it) (recommended); (b) not tried; NEEDS REVIEW when no skip
  link works.

**Draft rules.** DNA when the answer to Q1 is "no repeated block". A
candidate works when, after Enter, the next Tab lands past every stop of the
repeated block and not past the start of the main content: PASS when each
repeated block before the main content has a working method. Blocks with
no candidate, or every candidate broken (target missing, no move): FAIL.
A block the tool could not judge (Q1 unsure, frames, cap): NEEDS REVIEW.

**Fixtures.** W3C ACT cf77f2 cases (and their atomic rules) where DHS
scored them; Section 508 Baseline Alignment cases for Repetitive Content,
if the framework has them for 2.4.1. Custom pages: a skip link to a target
without tabindex (works in Chrome), a skip link to a missing id, a skip
link that lands past the main heading, a skip link visible only on focus
(4.D F03), two blocks needing two links, a page whose only bypass is a
landmark, a page with nothing before main (DNA under Q1).

**Time.** One replay per candidate (usually one or two): a few seconds.
